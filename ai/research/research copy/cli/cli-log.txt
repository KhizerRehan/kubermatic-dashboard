  Proposed Approaches

  Based on the exploration, here are 3 approaches for integrating Headlamp as a seed-side per-user-cluster deployment:

  ---
  Approach A: Direct Mirror of kubernetes-dashboard (Recommended)

  How it works: Create a new pkg/resources/headlamp/ package that is structurally identical to pkg/resources/kubernetes-dashboard/. Headlamp
  deployment runs on the seed in the cluster-xxx namespace with a kubeconfig secret pointing to the user cluster API server. Wire it into the
   existing cluster reconciler alongside the current dashboard.

  SEED (cluster-xxx namespace)              USER CLUSTER
  ─────────────────────────────             ─────────────
  Deployment: headlamp                      RBAC for kubeconfig cert user
    --kubeconfig /etc/kubernetes/kubeconfig    (Role + RoleBinding)
  Secret: headlamp-kubeconfig

  User-cluster side: Minimal RBAC only — a Role/RoleBinding granting the kubeconfig cert user (kubermatic:headlamp) access to cluster
  resources. No deployments in the user cluster (no metrics-scraper equivalent needed — Headlamp has its own built-in resource browser).

  Trade-offs:
  - (+) Proven pattern, minimal risk, easy to understand
  - (+) Reuses existing kubeconfig generation infrastructure
  - (+) Clean separation from old dashboard code
  - (-) Per-user-cluster overhead (one Headlamp pod per cluster)
  - (-) No plugin sharing across clusters

  ---
  Approach B: Seed-side with ConfigMap-based Multi-Cluster Config

  How it works: Same seed-side deployment, but instead of --kubeconfig, use Headlamp's --kubeconfig flag pointing to a multi-cluster
  kubeconfig (or multiple --proxy-urls). Still one Headlamp per user cluster, but architecturally prepared for future consolidation.

  Trade-offs:
  - (+) Could evolve toward shared instances later
  - (-) More complex kubeconfig management
  - (-) Headlamp's multi-cluster support may not work cleanly with kubeconfig-based auth
  - (-) Over-engineering for current requirements

  ---
  Approach C: Helm Chart Rendered Server-Side

  How it works: Instead of writing Go resource reconcilers, render the Headlamp Helm chart server-side and apply the manifests to the seed
  cluster namespace. Uses the chart as a source of truth but deploys to seed, not user cluster.

  Trade-offs:
  - (+) Stays aligned with upstream Helm chart
  - (-) Adds Helm rendering dependency to the controller
  - (-) Breaks the established Go reconciler pattern used by every other component
  - (-) Harder to customize for seed-side deployment (chart assumes in-cluster)

  ---
  My recommendation: Approach A. It's the lowest-risk path, follows the exact pattern that already works for kubernetes-dashboard, and keeps
  the codebase consistent. The per-cluster overhead is acceptable since KKP already runs ~10 deployments per user cluster on the seed.

  Key Differences from kubernetes-dashboard

  1. No metrics-scraper — Headlamp has built-in resource browsing, no sidecar needed
  2. ClusterRole instead of namespaced Role — Headlamp is a full cluster UI that needs read access to cluster-scoped resources (namespaces,
  nodes, CRDs, etc.)
  3. No JWE/CSRF secrets — Headlamp handles auth differently (kubeconfig-based)
  4. Different container flags — Headlamp uses --kubeconfig and --in-cluster=false instead of dashboard's --namespace and
  --enable-insecure-login
  5. Simpler user-cluster footprint — Only Namespace + ClusterRole + ClusterRoleBinding (no Deployments in user cluster)

  Secrets) — just the seed-side deployment with a kubeconfig.

  Yes, it should work. Here's why:

  The current kubernetes-dashboard needs those user-cluster resources because of its specific architecture:
  - metrics-scraper runs inside the user cluster to collect metrics from metrics.k8s.io — Headlamp doesn't need this, it queries the API
  server directly
  - JWE key-holder / CSRF secrets are specific to kubernetes-dashboard's authentication mechanism — Headlamp uses its own auth
  (kubeconfig-based when out-of-cluster)
  - ServiceAccount was for the metrics-scraper pod — no pods in user cluster means no SA needed

  How Headlamp works out-of-cluster:
  1. The headlamp-server binary accepts --kubeconfig flag pointing to a kubeconfig file
  2. It uses that kubeconfig to make API calls to the target cluster
  3. The kubeconfig will contain a client certificate with username kubermatic:headlamp
  4. The ClusterRole/ClusterRoleBinding in the user cluster grants that cert user read access
  5. Headlamp serves the web UI — users access it via the seed-side service/proxy

  What the user-cluster ClusterRole provides is the authorization for the kubeconfig cert user to read resources. Without it, all API calls
  from Headlamp to the user cluster would get 403 Forbidden.

  However — there's one open question I flagged in the spec: we need to validate the exact Headlamp server CLI flags (--kubeconfig,
  --in-cluster=false). This should be verified against the actual Headlamp binary before implementation.
